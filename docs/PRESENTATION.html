Motivation & Problem Statement

Why Traditional Retail Software Fails Under Load

Architectural bottlenecks that plague legacy Point-of-Sale systems

❌ The Polling Bottleneck

  • Dashboard screens query the database every 2–5 seconds (`GET /api/sales`).
  • Multi-register stores generate tens of thousands of redundant queries per hour.
  • Network bandwidth and database connection pools become oversaturated.

❌ Concurrency Overselling

  • Two cashiers scan the last remaining unit of an item at the exact same second.
  • Standard ORMs using un-locked reads both see `Stock = 1`, and both commit.
  • Result: Negative inventory (-1) and fulfillment failure.

✔ Our Architectural Solution

Sub-millisecond SignalR WebSockets push state updates only when transactions happen, and T-SQL Stored Procedures with UPDLOCK/ROWLOCK guarantee 100% ACID concurrency.

Speaker Note: Explain the real-world impact of overselling during flash sales and why HTTP polling wastes massive server CPU cycles.

Real-Time Core

Instantaneous Event Streaming via SignalR

Replacing polling with sub-15ms WebSocket push events

1. ReceiveInvoiceCreated

Fires the instant an invoice commits in the database. Pushes the full invoice DTO to the WinForms Live Ticker without manual refresh.

2. ReceiveLowStockAlert

Triggers automatically when an item's stock drops to or below its threshold. Displays a crimson banner & audio chime on all terminals.

3. ReceiveInventoryUpdate

Streams the updated stock quantity and low-stock flag. Updates the catalog in both WPF and WinForms in-place with zero flicker.

Thread-Safe UI Marshaling

Background socket threads cannot modify UI components directly. We safely marshal updates:

// In WPF:
Application.Current.Dispatcher.Invoke(() => Products[index] = updatedProduct);

// In WinForms:
BeginInvoke(new Action(() => gridLiveSales.Rows.Insert(0, invoice.InvoiceNumber, ...)));

Database Engineering

ACID Stored Procedures & Pessimistic Locking

Eliminating race conditions at the database level

sp_CreateInvoiceWithStockDeduction

  • `SET XACT_ABORT ON`: Automatically aborts and rolls back on any SQL exception.
  • `WITH (UPDLOCK, ROWLOCK)`: Acquires an update lock on the specific product rows being sold.
  • Stock Validation: Checks `CurrentStock >= Quantity`. If false, aborts before any insert occurs.
  • Audit Ledger: Inserts record into `dbo.InventoryMovements` with previous and new stock.

T-SQL Implementation Snippet

BEGIN TRANSACTION;
-- Lock targeted products & verify available stock
SELECT TOP 1 @InsufficientItem = p.Name
FROM @Items i
INNER JOIN dbo.Products p WITH (UPDLOCK, ROWLOCK) 
    ON i.ProductId = p.ProductId
WHERE p.CurrentStock < i.Quantity;

IF @InsufficientItem IS NOT NULL
    THROW 50002, 'Insufficient stock', 1;

-- Decrement stock and commit atomically
UPDATE p SET p.CurrentStock = p.CurrentStock - i.Quantity
FROM dbo.Products p INNER JOIN @Items i ON p.ProductId = i.ProductId;

COMMIT TRANSACTION;
Speaker Note: Point out why UPDLOCK is superior to naive table-level locking: it only locks the rows participating in the cart, allowing other cashiers to sell different items at full speed.
Database Performance

B-Tree Indexing & Query Plan Tuning

Optimizing high-frequency retail queries for sub-5ms seek execution

Covering Non-Clustered Index

CREATE NONCLUSTERED INDEX IX_Products_LowStock_Covering
ON dbo.Products (CurrentStock, LowStockThreshold, IsActive)
INCLUDE (Name, SKU, UnitPrice, CategoryId)
WITH (FILLFACTOR = 90);

Why INCLUDE? Attaching non-key columns directly to the leaf pages allows SQL Server to satisfy low-stock alerts through a pure Index Seek, completely eliminating expensive Clustered Key Lookups.

Unique Barcode Index

CREATE UNIQUE NONCLUSTERED INDEX IX_Products_SKU_Barcode
ON dbo.Products (SKU)
INCLUDE (ProductId, Name, UnitPrice, CurrentStock)
WHERE IsActive = 1;

$O(\log N)$ Scanner Seek: Guarantees instantaneous product resolution when cashiers scan barcodes or enter SKUs under rapid queue checkout.

Speaker Note: Explain how Key Lookups degrade database performance when tables reach hundreds of thousands of rows, and how covering indexes solve this.
